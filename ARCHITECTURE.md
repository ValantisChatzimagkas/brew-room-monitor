# Architecture

How the parts fit together and why. Rules for working inside each part live in the `CLAUDE.md` files; this is the map. It describes things that change rarely: if you change a boundary or a flow below, update this file in the same commit.

## Bird's-eye view

```
ESP32 / capsule ──device token──▶ POST /api/v1/readings ──────────────┐
laptop (curl)   ──user token────▶ POST /api/v1/devices  ──────────────┼─▶ FastAPI ──▶ Postgres
browser ──▶ Next.js server ──user token──▶ GET|POST|PATCH /api/v1/* ──┘
```

Devices push batches of readings. The backend stores them as rows of `(device, metric, value, recorded_at)`. The Next.js server reads them and renders HTML. The browser only ever talks to Next.js.

## Codemap

Start reading here, by flow:

- **Register a device:** from the dashboard, the page `frontend/src/app/devices/new/` and its `registerDevice` Server Action post with the signed-in user's token and return the device token once, in the action's response only (a room typed on the form is created first; if the user already has it, a 409, the action reuses that room); or with a user token from `curl` (`firmware/README.md` shows how to get one). `backend/app/routers/locations.py` creates the room, then `backend/app/routers/devices.py` creates the device pointing at it plus a random token, stores only its hash (`app/security.py`), and returns the plaintext once. Both rows belong to the caller. A lost device is cut off from its device page (`revokeDevice` in `frontend/src/app/devices/[id]/actions.ts`) or with `POST /api/v1/devices/{id}/revoke`, and re-keyed there too (`rekeyDevice`, the new token in the action's response only) or with `.../rotate`. `make seed` (`backend/app/seed.py`) does the same through the API for a local user, then posts demo readings and a batch.
- **Ingest:** `backend/app/routers/readings.py` `ingest_readings`. Auth comes from `current_device` in `app/deps.py` (token hash lookup; revoke replaces the hash, so a revoked token is just an unknown one). Payload bounds are in `ReadingBatch` / `ReadingIn`, metrics and units in `Metric`, allowed kinds and range per metric in `metric_spec` (`app/models.py`), the future-timestamp check in `MAX_CLOCK_SKEW`.
- **Track a brew:** `backend/app/routers/batches.py` creates, lists, ends and summarizes batches (device + time window; a user token creates, ends and sees only batches on their own devices, ownership derived through the device; per-metric min/max/avg/latest/count over the window, aggregated in Postgres; when the batch has a yeast range, the detail also reports how long the window's `temperature_c` readings spent below, inside and above it, each reading lasting until the next, capped, and turns those spans, split by phase since `started_at`, into hedged notes (rules and thresholds in `app/services/insights.py`; wording in the frontend)); the list takes `?device_id=` (a foreign device's id gives an empty list); `list_readings` in `routers/readings.py` takes `?batch_id=`. Both derive membership from the batch's device and window via `app/services/batches.py`. `list_readings` shows a user token only the readings of that user's devices.
- **Show:** `frontend/src/app/page.tsx` (formatting and staleness in `frontend/src/lib/metrics.ts` and `time.ts`) → `getApi()` in `frontend/src/lib/api/client.ts` → `GET /api/v1/devices` and `/readings` with the signed-in user's token, so each user sees only their own. The device detail page (`frontend/src/app/devices/[id]/page.tsx`) fetches per-metric `/readings` with `since` and `limit`, and hands plain `{time, value}` points to the client component `MetricChart`, which formats times in the browser's timezone. Below the charts it lists the device's newest batches (`GET /batches?device_id=`) with each one's summary, yeast range and below / inside / above split (all from `GET /batches/{id}`). While the device has no running batch and isn't revoked, that section links to the new-batch page. Each batch card links to the batch page (`frontend/src/app/batches/[id]/page.tsx`), which reads `GET /batches/{id}` and per-metric `/readings/buckets` (avg/min/max per time bucket via `date_bin` on a fixed UTC grid, bucket size from `pickBucket` in `frontend/src/lib/history.ts`) and charts the batch's window (open batch: to now) as the average line with a min–max envelope, and shows the batch's temperature notes with caveats (wording in `frontend/src/lib/yeast.ts`). On a running batch, its "End batch" form (`frontend/src/components/end-batch-form.tsx`) calls the `endBatch` Server Action, which `PATCH`es `ended_at` and refreshes the page. The new-batch page (`frontend/src/app/devices/[id]/batches/new/page.tsx`) and its form (`frontend/src/components/new-batch-form.tsx`) call the `startBatch` Server Action, which `POST`s the batch and opens its page.
- **Sign in (dashboard):** `frontend/src/proxy.ts` redirects a request with no session to `/auth/login` (except a Server Action POST, which its own `getApi()` redirects, since the action's `fetch` can't follow a 307) and lets the Auth0 SDK (`frontend/src/lib/auth0.ts`) serve `/auth/*`; the SDK keeps the session, access token included, in an encrypted httpOnly cookie, and `getApi()` reads the token from it (no session, or with Auth0 an expired token, sends the user back to sign-in; the local provider issues a refresh token, so there the SDK refreshes instead). The provider is Auth0 in production and the `oidc` compose service (a mock OIDC provider) locally; `AUTH0_DOMAIN` may be an `http://` URL outside production only. The backend then verifies that token as below.
- **Identify a user:** `verify_user_token` in `backend/app/oidc.py` checks signature, `iss`, `aud` and `exp` against the issuer's keys; `current_user` in `app/deps.py` maps the result to an `app_user` row (created on first request) and failures to 401, or 503 if the keys can't be fetched. `GET /api/v1/me` returns the caller's id. Routes that return or change an owner's rows take the `current_user` and filter with `owned` (`app/deps.py`), so another owner's row is a 404 (or 422 for a `location_id`), the same as a missing one.
- **Contract:** FastAPI generates OpenAPI → `make api-types` → `frontend/openapi.json` + `frontend/src/lib/api/schema.d.ts`. The device-facing part is written down in `firmware/README.md`.
- **Schema:** `backend/app/models.py` → Alembic migrations in `backend/alembic/versions/`.
- **Run/deploy:** `docker-compose.yml` (db, backend, frontend, with healthchecks, plus `oidc`, the local-only sign-in provider behind the `local-auth` profile, which `make oidc` starts and waits for; without this clone's key `make oidc` refuses and the provider won't boot), one `Dockerfile` per app, CI in `.github/workflows/ci.yml` (its `stack` job runs `make smoke`: builds the images and boots the compose stack).

## Boundaries and why they exist

- **The browser never calls the backend.** The user's token lives only in an encrypted httpOnly session cookie that the Next.js server reads (`server-only` client). So the backend needs no CORS and no sessions. Its callers are devices and users: a user is a verified JWT that the Next.js server forwards for a signed-in person, or that a person's `curl` sends. The only unauthenticated routes are `GET /health` and the OpenAPI schema (`/openapi.json` stays public in production; `/docs` doesn't).
- **Two token kinds.** A user token is a JWT from the hosted OIDC provider (`docs/decisions/0001-hosted-oidc-provider-for-user-sign-in.md`), verified against the issuer's public keys; the identity is `(iss, sub)` and the backend holds no secret for it. Each device gets its own random token, stored as a SHA-256 hash. A leaked device token only affects that one device, and a database leak doesn't expose usable tokens. A fast hash is enough because the tokens are 256-bit random, not passwords.
- **The local sign-in provider is dev only.** It signs in any username, so it's bound to loopback. It signs with a per-clone key that `make setup` writes to `.env`, because the image's own key is public: with that one, anyone who reaches the backend could mint any user's token. Both apps refuse an `http://` issuer under `ENVIRONMENT=production`, so a production frontend must set `ENVIRONMENT=production` too.
- **Plain HTTP on a trusted LAN only.** Tokens cross the network in cleartext, so put TLS in front (reverse proxy or tunnel) before the backend is reachable from outside the LAN. Postgres is bound to localhost in `docker-compose.yml` for the same reason.
- **Frontend writes only through Server Actions, frozen `/api/v1`, generated frontend types:** rules and reasons are in the root `CLAUDE.md` guardrails. What that means for the system's shape: those Server Actions call the same `/api/v1` with the user's token, and devices are registered from the UI or with a user token directly (`firmware/README.md`).

## Data model and why

- **One narrow `reading` table** (device, metric, value, time), not a column per sensor. A new metric is a new `Metric` value, not a new table or column, and because metrics are stored as strings it needs no migration.
- **A location is a room, as its own row** (name unique per owner, ignoring case), so devices in the same room group reliably and a device moves by changing `location_id`. `ambient` devices must have one; `in_vessel` devices may omit it, because their place will come from the vessel/batch they float in. The FK is `RESTRICT`, so a location with devices can't vanish.
- **Two timestamps.** `recorded_at` comes from the device (optional, because a device without NTP/RTC omits it and the server stamps the receive time). `received_at` is always server time. Timestamps clearly in the future are rejected, not stored, so a bad device clock can't corrupt history.
- **Validated readings.** A metric the device kind can't send, or a value outside its metric's physical range, rejects the whole batch. Ranges are sensor-wide on purpose: a 422 makes the device drop the batch, so the bounds stay wide enough for real sensor reads.
- **Locations and devices belong to one user (`owner_id`); readings don't.** A reading belongs to its device's owner by join, the same derived-not-stamped rule as batches, so ingest never needs the owner and a change of owner would not rewrite readings. Names (device, location) are unique per owner, not globally, so one owner's name never turns up as a 409 for another. A device and its location must share an owner; that's checked in the API where `location_id` is set, not by a constraint. The migration that adds the owner needs exactly one `app_user` whenever rows already exist (token recipe: `firmware/README.md`, "Getting a user token").
- **Devices are revoked (`revoked_at`), never deleted**, because their readings cascade on device delete.
- **Batched ingest** (bounds in `firmware/README.md`), because sending every few minutes saves device battery.
- **Ingest is idempotent.** A device-stamped reading is stored once per `(device, metric, recorded_at)`; a resend is a no-op, so a device that lost a 201 can retry its buffer. Readings without `recorded_at` are exempt, because they share the receive time and would clash. A partial unique index on `Reading` enforces it (`backend/app/models.py`).
- **A batch is a device plus a time window, not a stamp on readings.** Flashed devices can't learn about batches, buffered readings arrive late, and a batch can be created after its data exists, so a reading belongs to a batch when it comes from the batch's device with `recorded_at` in `[started_at, ended_at)`. A Postgres exclusion constraint (needs the `btree_gist` extension) stops one device having two overlapping batches, so the rule holds for any writer. A batch's summary is computed from that window on read, never stored. Batches are never deleted: a zero-length batch voids a mistake, and the FK to `device` is `RESTRICT`. A batch may carry its yeast's name and temperature range as its own nullable columns; there is no yeast table until two batches need to share one.
- **A user is `(issuer, subject)`, not an email.** The provider's `iss` + `sub` pair is the identity, so a provider swap or a second issuer can't merge two people. Stored in `app_user` (not `user`, which Postgres reserves); no email, name or roles.
- **Index `(device_id, metric, recorded_at)`** serves per-device and per-metric history; a second, partial unique index on the same columns does the dedupe. The dashboard reads the newest reading per device and metric (`limit=1`), which the index serves.

## Runtime and deploy

- **Sync endpoints, sync SQLModel session.** Simple and enough for this load; FastAPI runs them in its threadpool.
- **The backend is stateless and configured only by env**, so the same code runs in Docker or on FastAPI Cloud.
- **Migrations run on container start** (`backend/Dockerfile`), then the app `exec`s into PID 1 so it stops gracefully on SIGTERM. That's fine for one instance; move them to a release step before running more than one. On FastAPI Cloud, order by what the migration does: a new nullable column the new code reads (e.g. `device.revoked_at`) → migrate first, since old code ignores it (a NOT NULL one, like `owner_id`, makes old code's inserts fail, so deploy code and migration together, as the Dockerfile does); an added constraint (e.g. the reading dedupe index) → deploy the new code first, because it makes still-running old code return 500s until the new code is live.
- **Compose services report health, and the frontend starts only after the backend is healthy**, so `docker compose up --wait` returns when the stack is usable. The frontend's `GET /health` is public and independent of the backend.
- **The frontend reads env at request time**, not build time, so one image works in every environment.
- **Postgres only, no cache or queue.** Add one when a measured need shows up.

## Extending it

- **New metric:** add a `Metric` value → add its case in `metric_spec` (mypy forces this) → `make api-types` → add its entry to `METRIC_INFO` (typecheck forces this) and `METRIC_ORDER` (a test forces this) in `frontend/src/lib/metrics.ts` → list it in `firmware/README.md`.
- **New device type:** add a `DeviceKind` value if it differs from the existing ones, and add it to the `kinds` of each metric it may send in `metric_spec` (mypy does not catch a missing kind: its batches would all get 422). If it can't send the v1 payload, see `firmware/README.md` (Hardware notes) and the `/api/v1` guardrail.
